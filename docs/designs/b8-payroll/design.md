# B8 — الرواتب من الخادم: التصميم

| البند | القيمة |
|---|---|
| الحالة | الإصدار 2 بعد المراجعة المستقلة (`resolution.md`)، وقرارات القسم 10 محسومة (10 تشرين الثاني 2026) |
| التاريخ | 2026-11-10 |

| `official_holidays` (B7) | لا أثر على الراتب الشهري (ق-12 أيام فعلية)، ويُستعمل لاحقاً للعمل الإضافي |

## 3. نموذج البيانات

كل المبالغ `NUMERIC(18,6)`، والنسب `NUMERIC(9,4)`، والتواريخ `date`. لا `real` في أي جدول جديد.

### 3.0 إصلاح ما نعيد استعماله (شرط قبل أي احتساب)
1. **الحقول المؤثرة بالراتب تتغير بحركة مؤرخة فقط.**
   - الحقول: الدرجة، المرحلة، الشهادة، الحالة الاجتماعية، المسؤولية، موقع العمل، الوحدة، نوع الخدمة ونوع العقد، النقل المجاني، الخطورة.
   - التغيير عبر `applyMovement` بأمر وتاريخ نفاذ. التعديل المباشر من استمارة الموظف لهذه الحقول يُرفض، **إلا** عند الإنشاء أو بخيار «تصحيح خطأ إدخال».
   - **التصحيح** يكتب صفاً بـ `supersedes_id` يستبدل الصف الخاطئ من تاريخه نفسه، فما يتولّد مقطع وهمي.
   - **(تغيير سلوك يحتاج موافقة عمر — القسم 10.)**
2. **مشغّل السجل:**
   - يلتقط الإدراج (الموظف الجديد بصف أساس تاريخه تاريخ المباشرة).
   - يتتبّع `org_unit_id` بدل نص القسم والشعبة.
   - يتجاوز إعادة التسمية الجماعية (`hr.skip_history`) لأن الشروط والمستويات تُبنى على المعرّفات لا الأسماء.
   - يُوسَّع `normalizeFieldValue` للدرجات 11–13.
3. **«كما كان معروفاً في اللحظة T»:**
   - دالة `fieldAsOf(emp, field, day, knownAt)` تختار آخر صف `valid_from ≤ day` و`recorded_at ≤ knownAt` غير مُستبدل حتى `knownAt`.
   - الصف الأساس (`تقديري` بلا تاريخ) يُعامل معروفاً منذ الأزل.
   - صفوف `تقديري` و`تعديل مباشر` تظهر بتقرير المراجعة.
4. **سلّم الرواتب:**
   - النافذ لتاريخ = أحدث نسخة **معتمدة** تاريخ نفاذها ≤ التاريخ. علم `is_active` يصير مشتقاً للعرض فقط.
   - نسخة استُعملت بفترة محتسبة تُقفل بمشغّل: لا تعديل ولا حذف لخاناتها، والتغيير نسخة جديدة بأمر ومُعتمِد ثانٍ.
   - تاريخ نفاذ النسخة نقطة قطع للمقاطع.
5. **الترميزات المؤثرة** (فئة الشهادة القانونية، فئة المسؤولية، تصنيف الموقع، علم «يُصرف راتبه» للحالة، أب الوحدة التنظيمية) **لا تُخزَّن كأعمدة غير مؤرخة**. المستويات داخل `pay_item_versions` تُبنى بمعرّف الترميز: (معرّف الشهادة ← النسبة)، (معرّف الموقع ← المبلغ)، (معرّف المسؤولية ← النسبة). فتغيير مقابلة = نسخة بند جديدة بتاريخ وأمر ومُعتمِد. المقابلة تُبنى من شاشة واحدة لكل بند.

### 3.1 فئات الرواتب (ق-1)
`payroll_categories`: `code` (فريد، مثل `PERM`، `CONTRACT_<نوع>`، `DAILY`)، `name`، `kind` (دائم / عقد / أجر يومي)، `is_active`، `pay_basis` (شهري / يومي)، `notes`.
- انتماء الموظف للفئة = دالة على `service_type` و`contract_type` (حقل جديد، مؤرخ). جدول ربط `payroll_category_rules` (قيمة service_type + contract_type ← الفئة)، فتغيّر نوع خدمة الموظف يغيّر فئته من تاريخ النفاذ.
- B8: فئة `PERM` فعّالة فقط. باقي الفئات تُنشأ «غير فعّالة» حتى تُبنى بنودها.

### 3.2 البنود
`pay_items` (الخصائص الثابتة، القسم 6.1 من المتطلبات):
`code` فريد ثابت، `name`، `direction` (+/−)، `group` (الشهادة، المنصب، الموقع، العائلية، القانونية، العقوبات، الأقساط، القضائية، أخرى)، `classification` (عام / ثابت / تقديري / مؤقت)، `assignment_mode` (تلقائي / بأمر)، `method`، `category_id`، `payroll_code` (رمز كشف الرواتب للمطابقة)، `beneficiary`.

`pay_item_versions` (كل الخصائص المؤرخة بنسخة واحدة):
- `item_id`، `valid_from`، `valid_to` (فارغ = مفتوح).
- `props jsonb`، ويُتحقق من مخططه بالخادم: `value`، `levels[]`، `base` (مكوّنات الوعاء)، `caps` (سقف نسبة، سقف مبلغ، حد أدنى)، `inside_200_cap`، `in_retirement_base`، `employer_share`، `tax_effect`، `partial_behavior`، `calc_order`، `cap_reduction_priority` (ق-6)، `deduction_priority`، `withholdable`، `individual_override`، `conditions` (مجموعات «أو» من شروط «و»)، `legal_basis`، `verification` (مؤكد / يُتحقق)، `status` (مسودة / فعّال / موقوف / منتهٍ).
- `order_id`، `recorded_at`، `superseded_at`، `superseded_by`.
- `approval_state` (بانتظار الاعتماد / معتمد / مرفوض)، `entered_by`، `approved_by`، `published_at`.
- **قيد:** لا تتداخل نسختان معتمدتان غير مُستبدلتين لنفس البند (`EXCLUDE USING gist (item_id WITH =, daterange(valid_from, valid_to, '[)') WITH &&) WHERE (approval_state='معتمد' AND superseded_at IS NULL)`، يحتاج `btree_gist`).
- التصحيح لا يكتب فوق نسخة: يُعلّم القديمة `superseded_at` ويُضيف جديدة (مب3أ).
- **المستويات داخل `props.levels`** لأنها تتغير مع النسخة. قيد «لا قيمتين لنفس الحقل» يُفرض بالتحقق عند الحفظ.

### 3.3 بيانات الموظف المؤثرة
- **الحقول الملتقطة حالياً:** grade، step، job_title، department، section، work_location، status، service_type، primary_responsibility، acting_responsibility.
- **تُضاف للمشغّل:** education_level، marital_status، gender، contract_type (جديد)، free_transport (جديد، نعم/لا)، risk_exposure (جديد).
- **حقول ترميز ناقصة اليوم (خ2):**
  - `work_locations.geo_class` (نائية / ريفية / مركز ناحية / قضاء / محافظة).
  - `responsibility_allowances.legal_category` (فئة المادة 10: 30 / 25 / 20 / 15 / غير مشمول).
  - `education_degrees.legal_tier` (دكتوراه / ماجستير / دبلوم عالٍ / بكالوريوس / دبلوم فني / إعدادية / حرفة).
  - المستويات تُبنى على هذه الفئات القانونية، لا على أسماء الشركة. الموظف الذي فئته فارغة يظهر بقائمة «بلا مستوى» ولا يُمنح.
- **القومية والديانة ورقم الموظف لا تظهر حقولاً للشروط** (س7.1).

### 3.4 العائلة
البيانات اليوم JSON (`children_details`، `spouses_data`) بلا تواريخ نفاذ. تُنقل إلى:
- `family_members`: `employee_id`، `relation` (زوج/زوجة، ابن، بنت)، `name`، `birth_date`، `gender`، `source_ref` (المعرّف بالـ JSON القديم).
- `family_member_facts`: سجل إلحاقي بزمنين. `member_id`، `fact` (يدرس، متزوجة، موظفة، عاجز، حضانة بحكم، متوفى، الزوج موظف ويستلم الإعالة)، `value`، `valid_from`، `order_id`، `recorded_at`، `supersedes_id`.
- **نمط الاستحقاق العائلي** (كامل / الأطفال فقط / محجوب / لا يستحق) حقل مؤرخ بـ `employee_field_history` (`family_mode`).
- **الترحيل:** كل طفل بالـ JSON يصير عضواً، وحقائقه بتاريخ «تقديري» (س17.2). من عنده `children_count` بلا تفاصيل يظهر «بلا تفاصيل أطفال» ولا يُحتسب له إلا بعد الإدخال، لأن العمر شرط بالمادة 14.
- **الاعتماد:** إضافة فرد أو حقيقة أو تغيير النمط لا تكتب الجداول مباشرة. تُحفظ بـ `pending_operations`، وتُكتب عند الاعتماد (القسم 3.6). فالطفل المضاف بلا مُعتمِد لا أثر له (حالة 12).
- **التمديدات** (س8.5): جدول `family_extensions` (عضو، من، إلى، أمر).
- **الزوج الموظف بالشركة:** `family_members.spouse_employee_id` اختياري، لفحص «الزوجان يستلمان الإعالة معاً».
- **الترحيل بلا قيم مخترعة:**
  - النمط الأولي فارغ = «لم يُحدد»، ويظهر بفحص الجودة. البند `FAMILY` ما يتفعّل حتى يصفر هذا الفحص.
  - الأبناء بعمر 18–24 بلا حقيقة «يدرس» يظهرون بقائمة «يحتاج تأكيد الدراسة» قبل التفعيل.

### 3.5 الإسناد الفردي والحجب
`employee_pay_assignments`:
- `employee_id`، `item_id`، `kind` (منح / تعديل قيمة / حجب)، `value` (نسبة أو مبلغ، فارغ = قيمة القاعدة)، `valid_from`، `valid_to`.
- للأقساط: `principal`، `installment`، `count`.
- `order_id` (إلزامي)، `reason`، `approval_state`، `entered_by`، `approved_by`، `recorded_at`، `superseded_at`.
- **الحركات** (منح، تعديل، تمديد، إيقاف، إعادة، إنهاء، إلغاء) كلها صفوف جديدة. **الاستبدال والتقسيم يحدثان عند الاعتماد لا عند الإدخال**، بمعاملة واحدة: الصف المعتمد السابق يُعلَّم مستبدلاً، ويُكتب بدله صف ينتهي يوم قبل النفاذ الجديد، ثم الصف الجديد. فالمعلّق ما يشيل الصف النافذ.
- **التواريخ شاملة الطرفين بالعرض** («إلى» = آخر يوم)، وتُخزَّن `daterange` بصيغة `[من، إلى+1)`.
- **قيد التداخل** لكل (موظف، بند) عدا طريقتي `أقساط` و`يدوي بأمر` (س8.1)، بـ `EXCLUDE … WHERE (approval_state='معتمد' AND superseded_at IS NULL AND NOT multi_allowed)`. `multi_allowed` عمود منسوخ من طريقة البند. قيود EXCLUDE تُكتب SQL يدوياً بالترحيل، لأن drizzle ما يمثّلها، ويُتأكد أن `db:check` ما يعتبرها انحرافاً.
- تاريخ نهاية إلزامي للإسناد على بند تلقائي، وافتراضيه 12 شهراً (س8.3)، ما عدا الحجب المبني على واقعة.

### 3.6 العمليات بانتظار الاعتماد (مب9، س15.3)
`pending_operations`: `op_type`، `target` (الجدول والمعرّف)، `payload jsonb`، `entered_by`، `entered_at`، `state`، `decided_by`، `decided_at`، `decision_reason`.
- **مصدر واحد للحقيقة:** العملية الحساسة تُحفظ **حمولة فقط** بهذا الجدول، والجداول الهدف ما تشوفها. الاعتماد يطبّقها على الجدول الهدف بمعاملة واحدة مع سجل التدقيق. فجداول المدخلات تحمل المعتمد فقط، والمحرك ما يحتاج يفلتر حالات.
- **التعارض:** عملية معلّقة على هدف تغيّر بعد إدخالها تُرفض عند الاعتماد، ويُطلب إعادة إدخالها.
- **الفحوص بالخادم:** المعتمِد ≠ المُدخل. والمستخدم المرتبط بموظف لا يُدخل ولا يعتمد عملية على سجله (س15.3)، وهذا يحتاج عمود `users.employee_id` جديد (اختياري).

### 3.7 الفترات واللقطة
- **`payroll_periods`:**
  - `category_id`، `year`، `month`.
  - `kind` (عادية / استثنائية)، `parent_id`.
  - `pay_source` (ظلّي / فعلي).
  - `status` (مفتوحة / محتسبة / معتمدة / مُصدَرة).
  - `input_fingerprint`.
  - `computed_by/at`، `approved_by/at`، `issued_by/at`، `dispatch_letter`.
  - فريد: (category، year، month) للعادية.
- **`payroll_lines`:**
  - المعرّفات: `period_id`، `employee_id`، `item_id` (فارغ = الراتب الاسمي).
  - النسخ المستعملة: `item_version_id`، `scale_version_id`، `assignment_id`.
  - المقطع: `segment_from`، `segment_to`، `share`.
  - المبالغ: `base_amount`، `rate`، `amount` (دقيق).
  - `explain jsonb`: الشرط أو المستوى، السقف، السلوك، السند.
  - **نصوص مجمّدة:** اسم البند، العنوان، التشكيل، السند.
- **`payroll_results`:**
  - `period_id`، `employee_id`.
  - المبالغ: `nominal`، `allowances`، `deductions`، `net_exact`، `net`.
  - `flags jsonb`: سالب، بلغ السقف، تعذّر التقييم، بلا مستوى.
  - لقطة الموظف المجمّدة: الاسم، رقم الشركة، التشكيل، الدرجة والمرحلة.
- **`payroll_variances`:** تُشتق عند الاعتماد (س11.2). `period_id`، `employee_id`، `item_id`، `before`، `after`، `cause`، `order_id`.
- **الاحتسابات ثابتة:** كل احتساب `payroll_runs` (فترة، بصمة، من، متى، الحالة). السطور والنتائج تنتمي للاحتساب لا للفترة، والفترة تشير لاحتسابها الحالي. إعادة الاحتساب = احتساب جديد، والقديم يبقى (بدل جدول أرشيف).
- **مشغّلات:**
  - تمنع INSERT/UPDATE/DELETE على سطور ونتائج ومتغيرات أي احتساب ليس «جاري».
  - تمنع تغيير حالة الفترة إلا بالانتقالات المسموحة (11.1).
- **إلغاء الاعتماد:** يحتاج سبباً مكتوباً ومُعتمِداً ثانياً (س11.1)، ويحافظ على الاحتساب الملغى.
- **نسخة احتياطية** قبل كل اعتماد فترة (المتطلبات 18).

### 3.8 بصمة المدخلات
- **البصمة = تجزئة SHA-256 لمجموعة المدخلات القانونية نفسها اللي يبنيها المحمّل.** المجموعة مرتبة ومسلسلة لكل موظف، وتشمل:
  - بيانات الموظف المقروءة، ونسخ البنود ومستوياتها.
  - الإسنادات، والعائلة، وخانات السلّم.
  - حالات الموظف وعلم الصرف، وشجرة الوحدات.
  - (B8b) الإجازات والعقوبات.
- **تُحسب بنفس لقطة القراءة** اللي احتسبت الفترة (معاملة `REPEATABLE READ READ ONLY`). عند الاعتماد يُعاد التحميل والتجزئة؛ أي اختلاف يرفض الاعتماد (حالة 10).
- **الاعتماد** يعيد التحميل بلا احتساب، وكلفته ثواني.
- **قفل استشاري** لكل فترة (`pg_advisory_xact_lock`) يمنع تداخل الاحتساب والاعتماد.
- **انحراف مسجّل عن المتطلبات (11.1):** «إلغاء الاحتساب تلقائياً عند أول تغيير» صار «الاعتماد يرفض، والشاشة تفحص البصمة عند فتح الفترة». النتيجة نفسها بلا مشغّل على كل جدول.

## 4. المحرك

### 4.1 البنية
- `server/payroll/engine.ts` دالة **نقية**: `computeEmployee(inputs, period) → { lines, result, issues }`. لا قراءة قاعدة بيانات داخلها.
- `server/payroll/loader.ts` يحمّل كل مدخلات الفترة بقراءة واحدة لكل جدول (10.5)، ويبني لكل موظف `inputs`.
- `server/payroll/methods/*.ts` طريقة لكل ملف: `percent`، `flat`، `tiered`، `family` (B8a)، و`installments`، `manual`، `brackets` (B8b)، و`hours` (B8c).
- **الحساب العشري:**
  - وحدة `money.ts` على `bigint` بوحدة المليونية (1 دينار = 10⁶)، والنسب بوحدة 10⁻⁴.
  - كل قسمة تُقرَّب بنفس القاعدة (النصف بعيداً عن الصفر). نصيب المقطع يُطبّق بضرب ثم قسمة واحدة (المبلغ × الأيام ÷ أيام الشهر)، لا بنسبة مقرّبة مسبقاً.
  - لا `number` عائم بأي خطوة مالية. القيم من PostgreSQL تُقرأ نصاً (`NUMERIC` بـ `mode: 'string'`)، وتُسلسل للـ JSON نصاً.
- **مسار واحد (مب5):** شاشة المعاينة، والفترة، وقسيمة الموظف كلها تستدعي `computeEmployee`.

### 4.2 المقاطع
نقاط القطع داخل الشهر = اتحاد تواريخ:
- `valid_from` لكل حقل مؤثر بالسجل (كما عُرف وقت الاحتساب، القسم 3.0/3).
- بداية ونهاية نسخ البنود والإسنادات وحقائق العائلة.
- نسخة السلّم.
- **بداية الخدمة** = `current_appointment_date` أو صف الأساس بالسجل. **نهايتها** = تاريخ نفاذ تحوّل الحالة إلى حالة غير مشمولة بالصرف. التاريخ الناقص قضية جودة، والموظف ما يُحتسب له مقطع مجهول.
- تغيّر فئة الرواتب خلال الشهر: كل فئة تحتسب أيامها فقط.
- (B8b) بداية ونهاية حالات الاستحقاق.

كل مقطع يُحتسب كأن الشهر كله على حاله (س10.2، الخطوات أ–و)، ويُضرب بنصيبه = أيامه ÷ أيام الشهر الفعلية (ق-12).

### 4.3 خطوات المقطع
| الخطوة | العمل |
|---|---|
| أ | الاسمي من السلّم النافذ. موظف بلا درجة أو مرحلة ← لا راتب، وقضية «بلا درجة» (حالة 3) |
| ب | البنود داخل السقف بترتيب `calc_order`، كل منها على وعائه الكامل. الشرط الذي يتعذّر تقييمه لا يمنح، ويُسجَّل (حالة 4) |
| ج | سقف 200% (ت9) لكل مقطع على الاسمي الكامل: الزائد يُخفَّض من البنود بترتيب `cap_reduction_priority` الذي يحدده المدير (ق-6)، وسطر «تخفيض بسبب السقف» لكل بند مُخفَّض. **تفعيل بند داخل السقف بلا أولوية مرفوض** |
| د | البنود خارج السقف (العائلية، الظروف الخاصة، الإضافي) |
| هـ | حالة الاستحقاق (B8b؛ بـ B8a كل الأيام «دوام» ما لم يكن خارج الخدمة) |
| و | × نصيب المقطع |

الإسناد الفردي يتقدم على القاعدة (س8.3). الحجب = قيمة صفر.

### 4.4 الشهر
1. **تجميع** سطور المقاطع لكل بند، **بلا تقريب** (ق-18).
2. **التقاعد:** الوعاء = السطور الموسومة `in_retirement_base` (افتراضياً الاسمي المستحق)، والاستقطاع 10% (بند `RETIRE` مؤكد). **حصة الشركة 15% ما تُحتسب ولا تُعرض** حتى تتأكد (ق-15، مب8).
3. **الضريبة:** معطّلة (مسودة، ق-10).
4. **الاستقطاعات الأخرى** بأولويتها (B8b).
5. **الصافي الدقيق** = الاسمي + المخصصات − الاستقطاعات. **الصافي** = تقريب الدقيق لأقرب دينار، والنصف للأعلى.
6. **صافٍ سالب** (ق-7): يُصرف صفراً، وعلم «سالب» بالنتيجة. الترحيل رصيداً مديناً بدفتر الأرصدة يجي بـ B8b. بـ B8a البنود اللي تسبب السالب (الاستقطاعات الفردية) ما موجودة بعد، فالحالة نظرية.

**عرض السطور:** طريقة عرض الكسور سؤال لعمر (القسم 10/4)، لأن كشوف الجهات (التقاعد، المحكمة، النقابة) تحتاج دنانير كاملة لكل موظف، ومجاميع البنود لازم تطابق مجموع الصوافي. بعد الحسم تُعدَّل المتطلبات (10.2 الخطوة 1، والخاصية 18).

### 4.5 الشروط
- **العوامل:** يساوي، لا يساوي، ضمن قائمة، ليس ضمن، ≥، ≤، بين، فارغ، غير فارغ (س7.2).
- **الحقول:** B8a تقبل **الحقول المتتبَّعة بالسجل فقط** (القسم 3.0)، من قائمة ثابتة بالكود مع نوعها. حقل غير متتبَّع (طبيعة العمل، نظام المناوبة، العمر من الميلاد...) يُضاف للتتبع أولاً.
- **القيم الفارغة:** القيمة الفارغة أو النص البديل («سيتم تسجيله لاحقاً») = مفقودة ⇒ «تعذّر التقييم».
- **«التشكيل وما تحته»** يُقيَّم بـ `org_units` (B5) بالمعرّف، لا بالنص.
- **معاينة حيّة:** عدد المشمولين قبل/بعد، والأسماء، والأثر المالي، من `computeEmployee` نفسها على الشهر المفتوح. المدخلات المحمّلة تُخبأ دقائق، فالتعديل ما يعيد تحميل 6225 موظفاً.

## 5. دورة الفترة والصلاحيات

### 5.1 الانتقالات
كما بالمتطلبات (11.1)، لكل فئة رواتب منفصلة. بـ B8a: فتح ← احتساب ← اعتماد ← إصدار، وإلغاء الاعتماد قبل الإصدار. الدورات الاستثنائية بـ B8b.

### 5.2 أذونات الرواتب (جزء من B9 يتقدّم)
بالأدوار الثلاثة الحالية، المدير يدير المستخدمين ويعتمد الرواتب معاً، ويقدر يسوي حساب مدير ثاني ويعتمد عملياته بنفسه. لذلك تتقدّم من B9 **أذونات الرواتب لكل مستخدم**:
- **جدول `user_permissions`** (مستخدم، إذن، من منح، متى). الأذونات:
  - `payroll.read` (رؤية رواتب غيره والكشوف).
  - `payroll.compute`، `payroll.assign`، `payroll.family`.
  - `payroll.rules` (البنود والسلّم والمقابلات).
  - `payroll.approve` (الاعتماد الثاني واعتماد الفترة)، `payroll.issue`.
- **منح إذن رواتب عملية حساسة:** مدير النظام يُدخل، ومستخدم ثانٍ عنده `payroll.approve` يعتمد. ما أحد يمنح نفسه. كل منح بسجل النشاط ويظهر بتقرير الاستثناءات (س15.4).
- **مدير النظام ما يملك أذونات الرواتب تلقائياً** (س15.1). يقدر ياخذها مثل أي مستخدم، بس بنفس الاعتماد الثاني.
- **الربط بموظف:** `users.employee_id` **إلزامي** لكل من يحمل إذن رواتب. فحص «لا عملية على سجله» يُطبّق على كل مسار يكتب حقلاً مؤثراً بالراتب، ومنها استمارة الموظف القديمة.
- **الفصل بالمعرّف:** المحتسب ≠ المعتمد، والمُدخل ≠ المعتمِد. فلازم شخصان على الأقل بإذن الاعتماد، وتنبيه ظاهر إذا ما موجود غير واحد.
- **حالة 11 بـ B8a:** المحتسب يعتمد فترته، أو مستخدم يُدخل إسناداً أو فرد عائلة على سجله ⇒ مرفوض. جزء الحساب المصرفي يجي ويا المصرف (B8c).
- **B9 لاحقاً** يوسّع الجدول نفسه لباقي النظام بالأدوار المرنة.

### 5.3 الظلّي والفعلي (ق-14)
- إعداد `payroll.pay_source_default` = ظلّي. كل فترة تأخذ مصدرها عند فتحها.
- التحويل إلى «فعلي» عملية حساسة بيد المدير ومُعتمِد ثانٍ، ولا يمس فترات سابقة.

تُزرع بنود القسم 22 من المتطلبات **بحالة «مسودة»** لفئة `PERM`، بالقيم القانونية (لا بقيم HR-SYSTEM)، وكل قيمة بحالة تحققها:

| `GEO` | يُتحقق | تصنيف كل موقع عمل، وحقل النقل المجاني للموظفين |
| `FAMILY` | مؤكد عدا التوزيع بين الزوجين | نقل العائلة للجداول الجديدة ومراجعة «بلا تفاصيل أطفال» |

| `RISK`، `SPECIAL`، `OVERTIME`، `HEALTH`، `TAX`، حصة الشركة | يُتحقق / مسودة | قرار أو كتاب (ق-10، ق-15، ق-19) |
| `PEN_REDUCE`، `LOAN`، `RECOVER`، `COURT`، `UNION`، `INSURANCE`، `MANUAL_DIFF` | B8b | — |

- **التفعيل** يمر بمعاينة الأثر (عدد المشمولين، مجموع المبلغ، الأعلى والأدنى) ومُعتمِد ثانٍ، وبالشروط التالية:
  - تاريخ نفاذ التفعيل ما يسبق تاريخ أمره إلا بإذن أثر رجعي.
  - اتجاه البند يُقفل بعد أول فترة معتمدة.
  - الوعاء يُفحص ضد الدوائر.
  - اعتماد الفترة يُرفض إذا بند فعّال بقيمة «يُتحقق».
- **`salary_allowances` الحالي:** فيه منح فردية بأرقام أوامر (منصب، خطورة) وحسابات مصرفية. يُنقل **إسنادات مسودة** بانتظار المراجعة، والحسابات المصرفية تُحفظ للمرحلة 3.
- **أداة فحص جودة البيانات** (17.2) تعرض قبل التفعيل:
  - موظفين بلا درجة.
  - شهادات بلا فئة، ومسؤوليات بلا فئة، ومواقع بلا تصنيف.
  - أطفالاً بلا تاريخ ميلاد.
  - زوجين موظفين يستلمان الإعالة معاً.

  - يبقى الفصل بالمعرّف: المحتسب ≠ المعتمد، والمُدخل ≠ المعتمِد. فالكاتب يُدخل والمدير يعتمد، أو مديران.
  - فحص «لا عملية على سجله» يبقى لمن عنده `users.employee_id`، والربط اختياري.
  - **الخطر المقبول:** المدير يقدر يسوي حساب مدير ثانٍ ويعتمد لنفسه. المعالجة: كل إنشاء مستخدم أو تغيير دور يُسجَّل بسجل الرواتب الإلحاقي، ويظهر بقسم «تغييرات المستخدمين» بتقرير المراجعة لكل فترة. يُعالج نهائياً بـ B9.
- **(4)** الخيار (أ): استقطاعات الجهات (التقاعد، المحكمة، النقابة) تُقرَّب لكل سطر لأقرب دينار والنصف للأعلى، والمخصصات تبقى بكسورها، والصافي يُقرَّب.


**توقف B8a0:**
1. **الحقول المؤثرة بالراتب بحركة مؤرخة فقط** (3.0/1): الدرجة والمرحلة والشهادة والحالة الاجتماعية والمسؤولية والموقع والوحدة ونوع الخدمة ما تتعدل من استمارة الموظف إلا كتصحيح خطأ. التغيير الحقيقي بأمر وتاريخ نفاذ.
2. **أذونات الرواتب لكل مستخدم الآن** (5.2)، ومدير النظام ما ياخذها تلقائياً. ولازم شخصين بإذن الاعتماد.

**توقف B8a2:**
4. **التقريب:** كشوف الجهات تحتاج دنانير كاملة لكل موظف. الخيارات:
   - (أ) الاستقطاعات للجهات (التقاعد، المحكمة، النقابة) تُقرَّب لكل سطر، والمخصصات بكسورها والصافي يُقرَّب.
   - (ب) كل السطور بكسورها، وفرق التقريب يُضاف لسطر الراتب الاسمي.
   - (ج) كل السطور بكسورها بالكشوف (فلس).

**ما توقف التنفيذ:**
3. **صيغة الكشف الخارجي:** رؤوس الأعمدة ورموز البنود (مثل `m681`)، بلا أرقام حقيقية. لازمة لـ B8a4.
5. **المقابلات القانونية:** فئة لكل شهادة ومسؤولية وموقع، والنقل المجاني لكل موظف، ودراسة الأبناء 18–24. يدخلها مسؤول الرواتب بعد B8a1، والبنود تبقى مسودة لحد ما تكمل.
