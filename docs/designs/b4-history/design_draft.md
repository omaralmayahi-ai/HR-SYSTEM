# B4 — السجل الوظيفي المؤرخ والأوامر الإدارية (مسودة التصميم)

التاريخ: 2026-11-10 · يعتمد على: B1 (الترحيلات)، B3 (تقسيم الخادم) · القرارات: ق-4، ق-5، ق-14، ق-15

## الهدف
كل تغيير على بيانات الموظف الأساسية (الدرجة، المرحلة، العنوان، التشكيل، الحالة، نوع الخدمة، المسؤولية) يُسجَّل بتاريخ نفاذ، ويرتبط بأمر إداري إن وُجد، ويحفظ لقطة لحظة القرار. صف `employees` يبقى «الحالة الحالية» المشتقة من هذا السجل.

## B4a بالتفصيل

### المشكلة
قوائم الحالات مكتوبة يدوياً بأكثر من 15 موضعاً، وكل موضع يفهم «فعّال» بشكل مختلف:
- الرواتب (`salaryTable.js`): مستمر، مستمر بالخدمة، فعال.
- تراكم الإجازات (`leaveAccrual.ts`): نفس الثلاثة + الحالة الفارغة.
- لوحة المعلومات: فعال، مستمر، متقاعد مع تمديد.
- إعدادات المخصصات/الاستقطاعات، العقوبات، نموذج الموظف: قوائم ثابتة مختلفة.

### الحل
ترحيل 0006 يضيف لجدول `employee_statuses`:

| العمود | النوع | المعنى |
|---|---|---|
| `is_active` | boolean not null default false | يُحسب ضمن الموظفين الفعّالين (العدد، اللوحة، الاستحقاقات) |
| `payroll_eligible` | boolean not null default false | يُولَّد له راتب تلقائياً |
| `accrues_leave` | boolean not null default false | يتراكم له رصيد الإجازات الشهري |
| `sort_order` | integer not null default 100 | ترتيب العرض |
| `is_default` | boolean not null default false | الحالة الافتراضية للموظف الجديد (واحدة فقط، فهرس فريد جزئي) |
| `updated_at` | timestamptz | |

القيم الافتراضية بالترحيل (تطابق السلوك الحالي حرفياً، وأنت تغيّرها من الشاشة):

| الحالة | فعّال | راتب | إجازات |
|---|---|---|---|
| مستمر (افتراضية) | ✓ | ✓ | ✓ |
| مستمر بالخدمة، فعال (قيم قديمة إن وُجدت) | ✓ | ✓ | ✓ |
| متقاعد مع تمديد | ✓ | ✗ | ✗ |
| منسب، مجاز، متقاعد، مستقيل، موقوف، منقول | ✗ | ✗ | ✗ |

الترحيل يُدرج أيضاً كل قيمة `employees.status` موجودة وغير مسجلة بالجدول (بأعلام ✗)، فما تبقى حالة «يتيمة». الموظف بحالة فارغة يُعامل كالحالة الافتراضية (كما الآن).

### الخادم
- `server/statusRegistry.ts`: يقرأ الجدول مع كاش يُبطل عند أي تعديل؛ دوال `isActive(name)`, `isPayrollEligible(name)`, `accruesLeave(name)`, `defaultStatus()`, `namesWhere(flag)`.
- التراكم الشهري: `WHERE status = ANY($5) OR status IS NULL` بقائمة من السجل بدل النص الثابت.
- مسارات `/api/employee-statuses`:
  - GET يرجع الأعلام وعدد الموظفين لكل حالة.
  - POST (إنشاء) و PUT `/:id` (تعديل الأعلام والاسم والترتيب) للمدير فقط.
  - إعادة التسمية تحدّث `employees.status` و`leave`… كل الحقول النصية المخزنة بنفس المعاملة (employees فقط حالياً).
  - DELETE يُرفض (409) إذا الحالة مستعملة أو هي الافتراضية.

### الواجهة
- `useEmployeeStatuses()` هوك مشترك يقرأ من الخادم؛ يستبدل القوائم الثابتة في: Salaries، Reports، Dashboard، EmployeeForm، Penalties، إعدادات المخصصات والاستقطاعات، EmployeeImportSettings (القيمة الافتراضية).
- `isPayrollActiveEmployee(emp, statuses)` تأخذ السجل؛ بدون سجل (فشل الجلب) ترجع للسلوك الحالي.
- مدير الحالات الموجود بشاشة الموظفين يتوسع: مفاتيح الأعلام الثلاثة + الافتراضية + الترتيب.
- ألوان الشارات تبقى حسب الاسم مع لون محايد للحالات الجديدة.

### ق-15 منع الحذف النهائي
- `DELETE /api/employees/:id` (النقل للأرشيف) يبقى كما هو لأنه قابل للاسترجاع، لكنه يُرفض إذا للموظف سجلات (أوامر/ترفيعات/عقوبات/إجازات…) ويطلب تغيير الحالة لحالة غير فعّالة بدل الحذف. الحذف يُسمح فقط لموظف أُدخل خطأ وما عنده أي سجل.
- الحذف النهائي من الأرشيف لعنصر نوعه «موظف» يُمنع (403)؛ الاسترجاع يبقى.

### الاختبارات
- وحدة: statusRegistry (الكاش، الإبطال، الافتراضي، الحالة الفارغة).
- ترحيل 0006 على قاعدة اختبار: الأعلام الافتراضية، إدراج الحالات اليتيمة، فهرس الافتراضية الفريد.
- API: PUT يغيّر العلم ويؤثر على التراكم؛ إعادة تسمية تحدّث الموظفين؛ حذف حالة مستعملة 409؛ حذف موظف له سجلات 409؛ حذف نهائي لموظف مؤرشف 403.
- لقطة جرد المسارات تتحدث (PUT جديد).

## B4b بالتفصيل (للمراجعة الآن، التنفيذ بعد B4a)

### الجداول
`administrative_orders`: `id`, `order_number` text not null, `order_date` date not null, `issuer` text, `subject` text, `order_kind` text, `effective_date` date, `status` text check in ('نافذ','ملغى') default 'نافذ', `cancels_order_id` FK self, `document_id` FK documents null, `notes`, `created_by` FK users, `created_at`. فريد: (`order_number`, `order_date`, `issuer`).

`employee_field_history`: `id`, `employee_id` FK RESTRICT, `field` text check in (grade, step, job_title, org_unit, work_location, status, service_type, responsibility, acting_responsibility), `value` jsonb, `valid_from` date not null, `valid_to` date null, `order_id` FK null, `source` text check in ('تقديري','أمر','تعديل مباشر','ترحيل قديم'), `reason` text, `snapshot` jsonb (صف الموظف لحظة التسجيل), `recorded_at` timestamptz default now(), `recorded_by` FK users, `superseded_by` FK self null (تصحيح بدون فقدان الأصل).
قيد: لكل (employee_id, field) صف واحد مفتوح (`valid_to IS NULL AND superseded_by IS NULL`) — فهرس فريد جزئي.

### `careerMovements.apply(tx, { employeeId, effectiveDate, changes, orderId?, source, reason?, userId })`
1. يقفل صف الموظف (`SELECT … FOR UPDATE`).
2. لكل حقل متغيّر: يغلق الصف المفتوح (`valid_to = effectiveDate - 1`) ويُدرج صفاً جديداً. إذا التاريخ أقدم من صفوف لاحقة (أثر رجعي) يُدرج الصف بموضعه ويعيد ربط الحدود.
3. يحدّث `employees` إذا `effectiveDate <= اليوم`؛ التغييرات المستقبلية تُطبَّق عبر مهمة يومية `applyDueMovements()` عند الإقلاع وكل منتصف ليل.
4. يكتب سجل نشاط واحد.
كل شيء بمعاملة واحدة؛ أي فشل يرجع كل شيء.

### ق-4 سجل الأساس
أمر `db:history-baseline` (أداة + زر بلوحة التحكم) يُنشئ لكل موظف صفاً لكل حقل بمصدر «تقديري»: `valid_from` = أفضل تاريخ معروف (تاريخ الدرجة للدرجة، آخر علاوة للمرحلة، تاريخ التعيين للباقي) وإلا تاريخ التشغيل. idempotent: ما يكرر لموظف عنده صفوف.
