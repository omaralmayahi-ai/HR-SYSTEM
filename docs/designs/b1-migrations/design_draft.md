# B1 — ترحيلات قاعدة البيانات (Drizzle migrations)

الحالة: v1.1 بعد مراجعة Goldfish — 2026-11-09 (المعالجة في `resolution.md`) · يعتمد على: لا شيء · يمهّد لـ: B2، B3، B6

## 1. المشكلة (مقاسة)

- المخطط يُبنى اليوم بـ `ensureSchema()` في `src/db/index.ts`: 302 أمر DDL/بيانات يدوي يُنفَّذ **عند كل تشغيل**.
- `src/db/schema.ts` (مصدر أنواع Drizzle) **لا يطابق** ما يبنيه `ensureSchema`. قياس على قاعدتين فارغتين (PostgreSQL 16):
  - 52 جدولاً في الاثنين.
  - 46 عموداً موجوداً في القاعدة الفعلية وغير معرّف في `schema.ts` (منها 7 أعمدة مكررة بأسماء صغيرة في `governing_courses` مثل `coursename`، بقايا DDL قديم).
  - 34 عموداً تختلف قابلية الـ NULL أو النوع أو القيمة الافتراضية (أغلب الباقي `now()` مقابل `CURRENT_TIMESTAMP`، وهما متكافئان).
  - 24 فهرساً (منها 3 فهارس `gin_trgm_ops`) غير معرّفة في `schema.ts`.
  - 14 مفتاحاً أجنبياً معرّفة في `schema.ts` (`ON DELETE CASCADE`) **غير موجودة** في القاعدة الفعلية.
- `drizzle.config.ts` كان يتجاهل `SQL_PORT` ويطلب مفاتيح `SQL_ADMIN_*` لا تكتبها لوحة التحكم، فـ`drizzle-kit` لم يكن قابلاً للتشغيل أصلاً.
- لا يوجد سجل لما طُبّق على كل قاعدة، ولا طريقة لإضافة تغيير بنيوي إلا بإلحاقه في `ensureSchema`.

**B1a (هذا الفرع):** بنية ترحيلات تعمل على القواعد الحالية والجديدة **دون تغيير شكل أي قاعدة قائمة**.

| مواءمة `schema.ts` مع الشكل الفعلي | تحويل الأعمدة النصية إلى date/numeric |

| أوامر `db:generate` `db:migrate` `db:check` `db:status` | |
| دمج المرحّل بالتشغيل وبلوحة التحكم | |
| تجميد `ensureSchema` | |

سبب الفصل: B1b يغيّر بيانات حقيقية (6225 موظفاً) ويحتاج تقارير على قاعدة التشغيل قبل التنفيذ؛ B1a لا يلمس البيانات.

## 3. التصميم

### 3.1 مصدر الحقيقة
- بعد B1a: `src/db/schema.ts` هو مصدر الحقيقة للمخطط، و`drizzle/` (ملفات SQL + `meta/`) سجل التغييرات.
- `ensureSchema()` **يُجمَّد**: لا DDL جديد فيه بعد اليوم. **يبقى يعمل عند كل إقلاع** قبل الترحيلات (تعديل v1.1، M5) لأنه يحوي بذوراً وإصلاحات بيانات تعتمد عليها المسارات الحالية، ولأنه يبني الشكل الأساسي لأي قاعدة جديدة.

### 3.2 مواءمة `schema.ts`
- إضافة الأعمدة الـ46 بأسماء camelCase على نمط الملف، والأعمدة المكررة تُعلَّم `// legacy: يُحذف في B1b`.
- مطابقة NULL/النوع/الافتراضي مع القاعدة الفعلية. **تخفيف** `notNull` حيث القاعدة تسمح بـ NULL (آمن وقت التشغيل؛ قد يكشف أخطاء أنواع في TS تُصلَّح).
- إضافة الفهارس الـ24 بنفس الأسماء التي يستعملها `ensureSchema` (حتى لا يرى `drizzle-kit` فرقاً في الأسماء).
- **إزالة** تعريف المفاتيح الأجنبية الـ14 من DDL الجداول (`.references()`) لأن القاعدة الفعلية بدونها؛ تُضاف في B1b بترحيل مستقل. علاقات Drizzle (`relations`) — إن وُجدت — لا تتأثر.

### 3.3 ترحيل الأساس
- `npm run db:generate` يولّد `drizzle/0000_baseline.sql` من `schema.ts` المواءم.
- **شرط القبول:** قاعدة فارغة تُبنى بـ`ensureSchema` وأخرى بـ`0000_baseline.sql` (مع `CREATE EXTENSION pg_trgm`) تتطابقان في الجداول والأعمدة (الاسم، النوع، NULL، الافتراضي بعد تطبيع `now()`=`CURRENT_TIMESTAMP`) والقيود والفهارس. يتحقق منه السكربت `tools/db/compare-schemas.ts` واختبار يعمل حين يتوفر `TEST_DATABASE_URL`.

### 3.4 المرحّل `server/migrate.ts`
```
runMigrations():
  اتصال مخصص → pg_advisory_lock(<ثابت HR-SYSTEM>)
  ensureSchema()                      ← كل إقلاع (idempotent)؛ offline → توقف وإعادة محاولة لاحقاً
  إن كان جدول الترحيلات بلا صفوف (غير موجود أو فارغ):
     أخطاء ensureSchema؟ نعم → رفض التبنّي، لا يُسجَّل شيء
     فحص: كل جداول/أعمدة لقطة 0000 موجودة؟ لا → رفض التبنّي
     BEGIN; إنشاء الجدول + تسجيل 0000 (hash + when من journal) دون تنفيذه; COMMIT
  ترحيل مطبّق تغيّر ملفه، أو أقدم من آخر مطبّق ولم يُطبَّق → خطأ
  ترحيل في القاعدة لا يعرفه الإصدار → خطأ «حدّث أو استعد النسخة»
  migrate(db, { migrationsFolder: 'drizzle', migrationsSchema: 'drizzle' })   ← 0001 فما بعد
  pg_advisory_unlock
```
- **أخطاء الاتصال**: نفس سلوك اليوم (النظام يبدأ، الحالة `offline`، تُعاد المحاولة عند التشغيل التالي).
- **أخطاء غير اتصالية**: كل الترحيلات المعلّقة في **معاملة واحدة** (سلوك drizzle)؛ يفشل أيٌّ منها → rollback للدفعة كلها، الحالة `errors`، وتظهر في `GET /api/admin/schema-health`. النظام لا يتظاهر بالنجاح.
- القفل يمنع تشغيلين متزامنين (لوحة التحكم + الخادم) من التطبيق معاً.

### 3.5 الأوامر
| الأمر | ماذا يفعل | يكتب في القاعدة؟ |
|---|---|---|
| `npm run db:generate` | يولّد ترحيلاً جديداً من فرق `schema.ts` | لا |
| `npm run db:migrate` | `runMigrations()` (تبنٍّ + تطبيق) | نعم |
| `npm run db:check` | `drizzle-kit check` + فحص أن `schema.ts` لا يحتاج ترحيلاً غير مولَّد | لا |
| `npm run db:status` | المطبَّق/المعلّق + فروقات القاعدة الحية مقابل `schema.ts` | لا (قراءة فقط) |

### 3.6 التشغيل ولوحة التحكم
- `server.ts`: `await runMigrations()` بدل `ensureSchema()`.
- لوحة التحكم: «تحديث من GitHub» تأخذ **نسخة احتياطية إلزامية دائماً** قبل تطبيق التحديث (والترحيلات تُطبَّق عند الإقلاع)؛ أمر CLI جديد `control-app.bat migrate`؛ «فحص النظام» يعرض «الترحيلات: مطبّقة / N معلّق».

### 3.7 القواعد للمطورين (تُضاف إلى AGENTS.md)
1. لا DDL جديد في `ensureSchema` أبداً.
2. كل تغيير بنيوي: عدّل `schema.ts` ← `db:generate` ← راجع SQL ← التزم بالملفين معاً.
3. لا تعديل لترحيل مدموج؛ التصحيح بترحيل جديد.
4. ترحيل يحذف أو يحوّل بيانات يحتاج تقرير أثر على قاعدة التشغيل قبل الدمج.

## 4. المخاطر

| الخطر | التخفيف |
|---|---|
| قاعدة قائمة عمرها أقدم وتختلف عن شكل `ensureSchema` الحالي | التبني يشغّل `ensureSchema` أولاً (يكمل الناقص)، ثم يفحص؛ `db:status` يعرض أي فرق متبقٍ |
| ترحيل `drizzle-kit` لاحق يُولَّد بفرق وهمي (مثل `now()`) فيعيد إنشاء أشياء | شرط قبول 3.3 + `db:check` في الاختبارات |
| تخفيف `notNull` يكسر أنواع TS | `npm run typecheck`/`build` قبل الدمج |
| فشل ترحيل في منتصف التحديث | معاملة لكل ترحيل + نسخة احتياطية تلقائية قبله |
